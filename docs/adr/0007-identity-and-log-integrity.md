# 0007. Hash-chain the event log, sign C2SP checkpoints, and keep keys in the daemon

- Status: Accepted
- Date: 2026-09-26

## Context

Callsheet's record of what workers did is only useful if tampering can be
detected afterwards. Workers are untrusted: they run arbitrary tools on the
user's machine, so they must never hold signing keys. Integrity must be
designed into the log from the first event, because adding hashes later would
leave every existing log unverifiable.

Relevant specifications ([ADR 0005](0005-protocol-pins.md)):

- **RFC 8785** gives a canonical JSON serialisation, so the same event always
  hashes to the same bytes.
- **C2SP tlog-checkpoint v1.0.0** defines a checkpoint as a signed note whose
  text is three lines: the log's **origin**, the **tree size** in decimal, and
  the **root hash**, which is the base64 root of an **RFC 6962 Merkle tree**
  at that size. A log must never sign two inconsistent checkpoints.
- **C2SP signed-note v1.0.0** signs note text with Ed25519 (signature type
  `0x01`); the recommended key ID is the first four bytes of
  `SHA-256(key name || 0x0A || signature type || public key)`.
- **in-toto Statement v1** in a **DSSE v1.0.2** envelope is the standard
  shape for a signed claim about artifacts.

A simple hash chain (each event stores the previous event's hash) detects
edits and deletions in the middle of a log, but a chain head is not an RFC
6962 tree root, so it cannot be put in a C2SP checkpoint by itself.

## Decision

1. **Event hashing.** Fixed now, because feature 02 writes the first events
   and this cannot be retrofitted:
   - **Scope.** Each run has its own chain. Every event carries `run_id`,
     `seq` (starting at 1 and strictly increasing within the run),
     `prev_hash` and `event_hash`.
   - **Hash input.** `event_hash` is SHA-256 over the RFC 8785 canonical JSON
     of the event object with every field except `event_hash` itself.
     `prev_hash` is one of those fields, so it is hashed exactly once and is
     never appended separately.
   - **Encoding.** Every hash stored in an event is 64 lowercase hexadecimal
     characters.
   - **Genesis.** The first event of a run has `prev_hash` equal to 64 `0`
     characters (32 zero bytes).
   - **Content.** Events never embed message content. With content capture
     on, they reference a blob by its keyed content address
     ([ADR 0006](0006-capture-modes.md)); with it off, they carry no content
     reference at all.
2. **Checkpoints.** The daemon maintains one RFC 6962 Merkle tree per
   install. Leaves are appended in the order the daemon commits events,
   across all runs; each leaf's data is the 32 raw bytes of that event's
   `event_hash`, and each event records its leaf index. The daemon
   periodically signs a C2SP tlog-checkpoint of the tree (origin, size, root
   hash). Checkpoints contain hashes only.
3. **Keys and key separation.** Each install has two long-lived Ed25519
   keys, generated by the daemon, stored in the OS keychain and used only by
   the daemon. Workers never receive a private key.
   - The **root key** signs only DSSE envelopes, each with a
     Callsheet-specific `payloadType` (for example
     `application/vnd.callsheet.hire-record+json`), so DSSE's
     pre-authentication encoding keeps each kind of statement distinct.
   - The **checkpoint key** signs only C2SP signed notes, under a key name
     equal to the checkpoint origin. At install time the root key certifies
     the checkpoint public key in a DSSE statement.
   - Neither key signs bytes in any other format.
4. **Worker identity and attestations (feature 10).** At hire, the daemon
   mints an ephemeral Ed25519 key per worker, held only by the daemon. The
   root key signs a hire record (DSSE) containing the worker's public key,
   worker instance id, run id, task, spec digest, budget and expiry. At wrap,
   the daemon signs an in-toto Statement v1 in a DSSE envelope with the worker
   key, then destroys the private key. An attestation is verified along the
   path root public key → hire record → worker public key → attestation.
5. **Verification.** A `verify-log` command (feature 04) recomputes every
   chain and the tree, and checks checkpoint signatures, the checkpoint-key
   certificate, hire records and attestations.
6. **Wording.** Documentation calls the log **tamper-evident, not
   tamper-proof**: someone with full control of the machine and the keychain
   can rewrite history, but cannot do so without breaking checkpoints that
   were already exported or witnessed.
7. **No home-made crypto.** Hashing, signatures and canonical JSON use
   maintained libraries chosen from official docs in the feature that needs
   them; nothing in this ADR is implemented by hand.

## Consequences

- Feature 02 must hash-chain events from its first migration; this cannot be
  retrofitted.
- Feature 04 maintains two structures (per-run chains and one Merkle tree)
  and still has to define the checkpoint origin string and when checkpoints
  are signed. The hashing rules and leaf order above are already fixed.
- Canonicalisation bugs break verification, so RFC 8785 conformance needs
  test vectors before the log ships.
- Losing a keychain entry means no new signatures with that identity. Old
  checkpoints, hire records and attestations stay verifiable only if the
  public keys are recorded outside the keychain, so feature 04 must record
  them; key rotation needs its own design.
- Stronger guarantees (external witnesses cosigning checkpoints) remain
  possible later because the format is standard.
