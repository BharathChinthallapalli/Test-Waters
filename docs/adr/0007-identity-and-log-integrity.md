# 0007. Hash-chain the event log, sign C2SP checkpoints, and keep keys in the daemon

- Status: Accepted
- Date: 2026-09-26

## Context

Callsheet's record of what workers did is only useful if tampering can be
detected afterwards. Workers are untrusted: they run arbitrary tools on the
user's machine, so they must never hold signing keys. Integrity must be
designed into the log from the first event, because adding hashes later would
leave every existing log unverifiable.

Relevant specifications ([ADR 0005](0005-protocol-pins.md)):

- **RFC 8785** gives a canonical JSON serialisation, so the same event always
  hashes to the same bytes.
- **C2SP tlog-checkpoint v1.0.0** defines a checkpoint as a signed note whose
  text is three lines: the log's **origin**, the **tree size** in decimal, and
  the **root hash**, which is the base64 root of an **RFC 6962 Merkle tree**
  at that size. A log must never sign two inconsistent checkpoints.
- **C2SP signed-note v1.0.0** signs note text with Ed25519 (signature type
  `0x01`); the recommended key ID is the first four bytes of
  `SHA-256(key name || 0x0A || signature type || public key)`.
- **in-toto Statement v1** in a **DSSE v1.0.2** envelope is the standard
  shape for a signed claim about artifacts.

A simple hash chain (each event stores the previous event's hash) detects
edits and deletions in the middle of a log, but a chain head is not an RFC
6962 tree root, so it cannot be put in a C2SP checkpoint by itself.

## Decision

1. **Event hashing.** Every event stores `prev_hash` and
   `event_hash = SHA-256(RFC 8785 canonical JSON of the event || prev_hash)`,
   with a strictly increasing sequence number per run. Content is referenced
   by its SHA-256 blob hash, never embedded, so hashes never carry message
   content.
2. **Checkpoints.** The daemon also maintains an RFC 6962 Merkle tree whose
   leaves are the event hashes, and periodically signs a C2SP tlog-checkpoint
   of it (origin, size, root hash). Checkpoints contain hashes only.
3. **Keys.** Each install has one Ed25519 root key, generated by the daemon
   and stored in the OS keychain. Only the daemon uses it. Workers never
   receive any private key.
4. **Worker identity and attestations (feature 10).** At hire, the daemon
   mints an ephemeral per-worker Ed25519 key, held only by the daemon, and the
   root key signs a hire record. At wrap, the daemon signs an in-toto
   Statement v1 in a DSSE envelope with that key, then destroys the key.
5. **Verification.** A `verify-log` command (feature 04) recomputes the
   chain and tree and checks every checkpoint signature.
6. **Wording.** Documentation calls the log **tamper-evident, not
   tamper-proof**: someone with full control of the machine and the keychain
   can rewrite history, but cannot do so without breaking checkpoints that
   were already exported or witnessed.
7. **No home-made crypto.** Hashing, signatures and canonical JSON use
   maintained libraries chosen from official docs in the feature that needs
   them; nothing in this ADR is implemented by hand.

## Consequences

- Feature 02 must hash-chain events from its first migration; this cannot be
  retrofitted.
- Feature 04 has two structures to maintain (chain and Merkle tree) and must
  define the checkpoint origin string, how per-run sequences map to tree
  leaf order, and when checkpoints are signed.
- Canonicalisation bugs break verification, so RFC 8785 conformance needs
  test vectors before the log ships.
- Losing the keychain entry means no new checkpoints can be signed with the
  same identity. Old checkpoints stay verifiable only if the public key is
  recorded outside the keychain, so feature 04 must record it; key rotation
  needs its own design.
- Stronger guarantees (external witnesses cosigning checkpoints) remain
  possible later because the format is standard.
